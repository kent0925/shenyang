## Blocker hardening follow-up

- Upload no longer stores binary chunk files or assembles a full byte array in GAS. Each chunk is SHA-256 verified (and first-chunk magic validated), then sent directly through OAuth-authenticated UrlFetch to a server-only Drive resumable session. Stable generated Drive IDs, session status accepted offsets and immutable per-index digests make retries idempotent. Finalize reads metadata only and confirms final Drive size. Global ScriptLock never encloses HTTP/binary work; final authoritative FormRecord CAS remains immediately before publish. Pending session cancellation and file trash happen outside lock on conflict. Session/digest metadata is removed after publish.
- Normal upload and retry are separate hook methods. Unresolved retries guard formal save, disable both add controls and retain original form/version. Failed pending items can be discarded from both pending and retry state; uploading items cannot. Discarding the last failure clears retry state and restores normal save. Published attachments have no delete UI/API.

## Bounded download and abandoned-upload cleanup follow-up

- `handleGetFormAttachmentFileChunk` resolves form/version/attachment to a published file on the server, rejects client fileId, and requests only `bytes=start-end` from Drive `alt=media`. HTTP 206 must match Content-Range and expected byte length; HTTP 200 is accepted only for a complete single-chunk file. Raw response bytes must equal the range length and stay <= 2097152 bytes. Large-file HTTP 200 is rejected before extracting response bytes. Frontend rebuild still checks final size and whole-file SHA-256. Protocol reference: https://developers.google.com/workspace/drive/api/guides/manage-downloads .
- `cancelFormAttachmentUpload` is metadata-only, routed through GAS and the proxy payload boundary. It authoritatively resolves the Form and uses the existing attachment lease, but allows stale expectedVersion solely for pending cleanup. Only `.pending-ATT-UUID` is resolved; missing pending is success. Session abort is attempted, temporary file is trashed via metadata PATCH (404 means already absent), then folder is trashed. Temporary-file cleanup failure preserves pending and returns failure rather than claiming success. Published packages are never selected or deleted.
- Failed discard awaits backend cancel before clearing local pending/retry. Cancel failure retains the failed item with `附件暫存清理失敗，請再試一次。`. Cancellation disables processing controls. Reset/load handlers guard unresolved retries, and hook clear also refuses to drop unresolved state.
